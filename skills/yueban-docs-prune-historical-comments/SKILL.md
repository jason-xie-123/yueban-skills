# yueban-docs-prune-historical-comments：清理历史变更叙事类注释/文档段落

## 范围（发现方式与排除规则与 `yueban-docs-freshness-audit` 对齐，覆盖的文件类型不同）

不要在这个文件里手写"仓库里现在有哪些 submodule"这种会随项目演进而过期的清单，每次执行都从 `.gitmodules` 动态取得（命令见第 2 步）。项目专属的细节（比如"哪个目录是历史规划归档、不算当前产品文档""某个冻结模块为什么被排除"）当场问用户或从项目自己的 AGENTS.md/README.md 里找依据，不要凭经验/凭上次执行的记忆假设。

- **每个当前维护的 submodule**——动态来源是 `.gitmodules` 里路径不以 `deprecated/` 开头的条目（具体有哪些以 `.gitmodules` 当前内容为准，新增/移除 submodule 会自动跟着变，不需要改本文件）：整个 submodule 内所有匹配下方"文件类型"的文件，不限于顶层 `README.md`/`AGENTS.md`——包括各模块源码目录下的注释、以及 `docs/` 子目录（如果该 submodule 有的话）下的 Markdown 文档。
- **根仓库自身：`README.md`/`AGENTS.md` 两个文件，以及整个 `docs/` 目录**（排除已确认的历史规划归档子目录，若存在；根仓库如果没有源码，只适用 Markdown 规则）。`docs/` 下内容如果以 PRD/背景知识等产品资料为主，处理时按下方「判定标准」末尾的专门提示格外谨慎判断，不要套用工程文档（AGENTS.md/README.md）的经验直接删。
- **明确排除**（理由各不相同，分别判断，不要因为都叫"排除"就混为一谈）：
  - `deprecated/` 整个目录树（含所有历史/冻结子仓库）。如果项目里有某个冻结/历史模块被其它文档明确依赖用来做同步比对（比如根 AGENTS.md 里写明了"要靠某个历史模块的现有内容和当前分支比对，判断哪些改动需要补等价实现"），这类模块不适用本 skill——本 skill 会删除的"历史回溯叙事"正是这类同步流程依赖的信息，两者目标冲突。执行前如果不确定某个 `deprecated/` 模块是否有这类特殊用途，先问用户或查根 AGENTS.md，不要假设所有 `deprecated/` 模块都是单纯的死仓库。
  - 项目里明确标注为历史功能规划归档的文档目录（如果存在）——本质是历史规划产物，不是需要维护时效性的业务资料，跟这个 skill"清理不再有指导意义的历史叙事"的目标不同——这批文件整体就是历史记录，不适合按段落粒度去清理。具体路径按项目约定，执行前先确认，没有明确依据不要自己认定某个目录属于这一类。
  - `openspec/changes/` 整个目录（若项目使用 openspec，含顶层未归档的和 `archive/` 下已归档的）——`proposal.md`/`design.md`/`tasks.md` 是某次具体 change 的过程性工作文档，本身就是合法的变更历史载体，不是这个 skill 要清理的对象（本来也不在本 skill 的枚举命令覆盖范围内，这里明确写出来避免被误解为遗漏）。
- 文件类型：
  - 源码注释：`.java`、`.ts`、`.tsx`、`.js`、`.jsx` 文件里的 `//`、`/* */`、`/** */`（如果项目主要语言不同，按实际语言的注释语法调整，原理不变）。
  - Markdown 文档：`.md` 文件（README、AGENTS.md 等）正文段落。
- **明确排除，不清理：**
  - `@deprecated`/`@Deprecated` 标注及其说明（对调用方仍有实际指导价值）。
  - 项目里如果有版本化的数据库迁移文件目录（比如 Flyway/Liquibase 一类工具生成的按版本号命名的 SQL 迁移文件），这类文件本身（文件名和文件内注释都不动）——迁移文件本身就是变更历史的合法载体，不是"写在别处描述过去"的那种注释。这类目录的具体路径按项目约定，执行前先确认，没有则跳过这条排除规则。

## 判定标准

**清理对象**：注释/文档段落中描述"这段代码/规则/测试是如何从过去的状态变成现在的状态"的历史回溯叙事。不要求是 AI 生成的——只要内容在记录历史变更过程，不论作者是谁，都算清理对象。

典型特征（不限于，供子 agent 判断时参考，不是穷举关键词表）：
- "原本是……后来因为……改成"
- "随某次版本/迁移删除/变更"
- "迁移自旧模块/旧实现"
- "不复述某次改动前已有的……"
- "该测试原位置留下的说明注释""历史数据合并逻辑原先由……覆盖，随……移除"这类叙事结构
- "design.md / tasks.md 决策 X" 且该引用只是在交代"这条规则是怎么定下来的过程"（如"改判为……""施工阶段补的接口……design.md 未预先设计"），本身对理解当前行为没有增量信息。

**反例（不清理）：**
- `@deprecated` 说明，即使提到"原来做什么用、为什么废弃"，只要仍对调用方有实际指导价值（如指向替代方案）。
- 单纯提到版本号/日期但不构成"过去如何、后来如何变化"叙事的内容（如"需要 Java 17+"）。
- 版本化的数据库迁移文件本身（如果项目有这类目录）。
- "design.md / tasks.md 决策 X" 引用如果是在为**当前仍生效的设计取舍**提供依据（如"为什么这个 Mapper 不提供 update/delete，见 design.md 决策 N"），不是在叙述"怎么从旧状态变成新状态"，保留；判断标准是去掉这句引用后，读者是否还能看懂"现在为什么这样做"——看不懂就保留，看得懂就属于可删的纯历史标注。

**处理根仓库 `docs/` 时额外注意**：这个目录下如果是 PRD、背景知识等产品/业务资料，不是工程文档，"原本怎样、后来因为……改成怎样"这类句子在这里往往是需求变更的决策留痕（为什么当前这条业务规则长这样、之前考虑过什么方案），对理解"现在为什么这样定"有实际参考价值，不能直接套用上面"看不懂就保留，看得懂就删"这条工程文档的经验——产品文档里"看得懂现在的结论"不代表"决策过程的记录就没有价值"，拿不准的一律按「反例」处理、不删，记入存疑。如果项目自己的文档里已经写明了多份 `docs/` 子目录之间的权威性关系，处理前先读一遍，避免删除内容后改变了这些文档的相对权威性结论。

## 清理粒度（按文件类型区分，不要混用同一套规则）

- **源码注释**：一个注释块（一条 `//`、一个 `/* */`、一个 `/** */`）只要内容里出现历史叙事，**整块删除**。不做"保留仍然有效的那部分、只删历史部分"的细粒度改写——代码注释块通常短，历史叙事和当前有效信息混在一起很难干净拆句，且删完不影响代码本身的可读性（代码本身不应该靠这种注释才能被理解）。
  - **例外：注释块里混有"载体性不变量/约束"（landmine）时，不能整块删除，要改写成保留该约束、去掉历史叙事的现在时说明。** 判断标准：这条信息如果被删掉，未来有人改代码时会在不知情的情况下悄悄破坏正确性（例如"这个方法必须挂 `@Transactional`，否则并发下会丢更新""这个字段固定为 X，不能走通用解析路径，否则真实数据下会抛异常"），而不是仅仅"读起来方便"。纯粹的背景八卦、施工阶段花絮、决策编号引用不算此类例外，按上面的整块删除处理。这类改写只在真正遇到时做，不要为了"保险"就到处保留。
- **Markdown 文档**：文档段落通常比代码注释大得多，常见结构是"一句历史背景过渡 + 一大段仍在生效的操作指南"（例如"因为过去 XX 曾导致 YY 问题，现在要求每次都按以下步骤……"）。这种情况**只删历史叙事的句子/小段，保留后面仍然生效的操作指南/规则本身**，不要整节删除。

## 执行流程

### 第 1 步：现场询问扫描识别方式

用 AskUserQuestion 问用户本次用哪种方式（**每次运行都要问，不要复用上次的选择，也不要自己替用户决定**）：

- **AI 逐文件通读判断**：不依赖关键词，由子 agent 通读分组内每个文件正文，靠语义判断是否为历史叙事。覆盖更全，但更慢、更耗 token。
- **关键词预筛 + AI 复核**：先用 grep 关键词圈出候选文件/候选行，子 agent 只复核候选是否真的该删。更快，但可能漏掉不含常见关键词的历史叙事。

关键词参考（仅用于"关键词预筛"模式，子 agent 可按分组内容自行补充，不要求穷举）：
`原本|原来是|后来因为|随.{0,10}(删除|变更|迁移)|design\.md|tasks\.md|迁移自|已废弃的旧|决策 ?\d`

### 第 2 步：枚举并分组文件

```bash
# 当前维护的 submodule：从 .gitmodules 动态取得（排除 deprecated/ 前缀），不要硬编码模块名
mapfile -t ACTIVE_SUBMODULES < <(git config -f .gitmodules --get-regexp '\.path$' 2>/dev/null | awk '{print $2}' | grep -v '^deprecated/')
for sm in "${ACTIVE_SUBMODULES[@]}"; do
  git -C "$sm" ls-files -- '*.java' '*.ts' '*.tsx' '*.js' '*.jsx' '*.md' \
    | sed "s#^#$sm/#"
  # 如果该 submodule 有版本化数据库迁移目录（Flyway/Liquibase 等），在上面加一条
  # grep -v '^<迁移目录相对路径>/' 排除掉，具体路径按项目实际情况确认
done

# 根仓库自身
git ls-files -- README.md AGENTS.md 'docs/*.md' 'docs/**/*.md'
# 如果 docs/ 下有已确认的历史规划归档子目录，在这里加 grep -v 排除掉
```

`'docs/*.md' 'docs/**/*.md'` 两个 pattern 必须一起用——`**/*.md` 要求至少一层子目录，单独用会漏掉 `docs/README.md`、`docs/AGENTS.md` 这类顶层文件；每个 submodule 用的是不带路径前缀的 `'*.md'`，不受此限制，能自动匹配到任意深度的 `.md` 文件，不需要同样处理。

按以下原则动态分组派发（每组一个子 agent；组数随当前 submodule 数量/体量变化，不固定）：

- 对每个当前维护 submodule，按其顶层目录/模块结构分组，体量大的模块拆多组、体量小的合并成一组（具体怎么拆按该 submodule 实际的模块划分来定，如果它自己的文档里写了模块划分说明就参考那份说明；没有就按顶层目录粗分）。每个 submodule 各自的 `docs/` 子目录（如果有）归入该 submodule 顶层文件那一组一起处理。
- 根仓库 `docs/` 按其下实际存在的子目录划分分组（排除已确认的历史规划归档目录），子目录内文件较多时可再拆；每组子任务 prompt 里额外附上「处理根仓库 `docs/` 时额外注意」那段内容
- 根仓库自身的 `README.md`、`AGENTS.md`（两个文件体量小，跟其中一组合并派发即可，不必单独开一个 agent）

### 第 3 步：并行派发子任务

对每个分组用 Agent 工具派发一个 `general-purpose` 子任务，**在同一条消息里一次性并行发出**。子任务 prompt 必须完整包含本文件"判定标准"（含"处理根仓库 `docs/` 时额外注意"那段）"清理粒度（按文件类型区分，不要混用同一套规则）""明确排除，不清理"三节的原文内容（把文字直接粘贴过去，不要只给一个文件路径让子 agent 自己去读——子 agent 是全新上下文，看不到这个 SKILL.md）。派给根仓库 `docs/` 分组的子任务，额外在 prompt 里强调一句：这批文件是产品/业务资料，不是工程文档，拿不准一律按「反例」处理、不删，宁可漏改也不要误删决策留痕：

```
你的任务：清理 <分组路径> 目录下源码注释和 Markdown 文档里记录"历史变更过程"的内容。

【判定标准】
（粘贴上面"判定标准"整节内容）

【清理粒度】
（粘贴上面"清理粒度"整节内容）

【明确排除】
（粘贴上面"明确排除，不清理"整节内容）

【本次扫描识别方式】
（"AI 逐文件通读判断" 或 "关键词预筛 + AI 复核"；若是后者，把上面的关键词参考也带过去）

【执行方式】
直接用 Edit 工具修改文件，不要先列候选清单等待确认——用户会自己用 git diff 复核你的改动。改完用一句话总结你改了多少个文件（列出文件路径），不要生成额外的报告文件。
```

### 第 4 步：汇总

收到所有子任务的摘要后，合并成一句话汇总（改了几个文件、分布在哪些目录）回复用户，不生成报告文件。提醒用户可以用 `git -C <submodule路径> diff`（每个当前维护的 submodule 各跑一次）以及根仓库自身文件与 `docs/` 用 `git diff` 复核改动。

## 可复用性

不依赖任何一次运行的具体文件列表或历史结果，每次调用都重新执行"枚举 → 现场问识别方式 → 分组派发 → 汇总"这个完整流程。仓库里以后再新增历史叙事类注释，直接重新运行 `/yueban-docs-prune-historical-comments` 即可，不需要额外维护状态。

## 不做的事

- 不处理 commit message、PR description。
- 不处理 `deprecated/` 下已确认有特殊同步用途的历史/冻结模块（见上方「明确排除」）。
- 不生成候选清单等待二次确认。
- 不对源码注释做"保留关键信息、改写成正常注释"的处理——按上面的规则整块删除。
- 不自动 commit。是否提交、何时提交由用户决定，遵循仓库自己 `AGENTS.md`「提交约定」（仅在用户明确要求时才创建 git commit）。
