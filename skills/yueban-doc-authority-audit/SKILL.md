# yueban-doc-authority-audit · 对照官方权威来源的四维度文档审计

## 概述

将一份文档与**外部权威来源**逐行交叉核对（典型场景：一份支付/合规手册对照 docs.stripe.com / docs.adyen.com / developer.apple.com / Play Console 帮助文档；SDK 集成对照 API 参考文档；合规内容对照实际法规原文；技术规范对照 RFC/W3C/ISO）。

**核心约束**：

- 事实来源只能是**权威一手文档**，不能是二手聚合页面、行业常识、跨厂商推断、内部 wiki，或 AI 的训练记忆
- 同一维度的理解与审查必须**独立进行**，不能在同一次注意力里既理解又审查同一件事，会让幻觉自我确认；但 §1/§2/§3/§4 四个维度彼此独立，可以并行执行（维度之间没有"边读边判"的问题）
- **先提取声明，再分批核实**——把同类型声明归到一起，成批对照权威来源核实，比逐句扫描更容易发现跨章节冲突；这条规则应用在 §3 事实正确性维度的内部执行中
- 默认执行**多轮（最多 3 轮）× 并行四维度审计 → 主agent仲裁修复**的闭环，不是一次性只报告；收敛、暂停、输出规则见下方「工作流程」

## 何时使用

仅当**用户明确指名此技能**时触发（例如 `/yueban-doc-authority-audit` / "用 yueban-doc-authority-audit 处理一下" / "跑一下对官方来源的审计流程" / "跑一下四维度审计流程" / "跑一下多轮审计修复流程"）。触发后默认按下方「工作流程」执行多轮审计+自动修复，不再是仅报告的单轮模式。

**不应自动触发的反例**——看起来匹配但仍需用户明确指名此技能：

- 用户只说"审计一下这份文档"/ "帮我对照官方文档核实一下" —— 这是普通的文档核查，按常规方式处理，不必强行套用本技能的四维度+三段式输出
- 用户提到逐字比对/四维度/三段式输出，但没有指名此技能

**不适用于**：普通代码审查（`requesting-code-review`）/ 文档对照代码库漂移的核查（事实来源不同的另一类审计）/ 草稿阶段（`brainstorming`）。

## 事实来源优先级（硬性约束）

| 层级 | 来源 | 能否作为引用依据 |
|---|---|---|
| ⭐ 一级 | 权威一手规范文档（官方开发者文档 / API 参考 / RFC / 标准文本 / 法规原文） | ✅ 唯一可作为证据的层级 |
| 二级 | 官方公告 / 变更日志 / 官方博客 | ✅ 可用于历史背景 / 确定切换时间点 |
| 三级 | 二手帮助中心 / FAQ 聚合 / 平台级二手 wiki | ⚠️ 仅作交叉验证辅助，不能单独作为证据 |
| ❌ 禁止 | 销售页面 / 宣传文案 / 行业博客 / 跨厂商推断 / 内部 wiki / Stack Overflow / 转载 | ❌ 不能作为证据 |

**引用时必须**：附完整 URL 并在线核实，并满足 §1 中的每一条（见下方四维度检查清单）。

**另外**：**AI 的训练记忆**（"应该是 X" / "据我所知，Y"）不属于以上任何一个层级——**任何可核实的声明都不得以训练记忆背书**；必须在阶段 2 在线核实，或标注为"未找到官方依据"。见"常见错误"中的"用训练记忆填数值"。

## 四维度检查清单

### §1 超链接 / 引用

- URL 是否可访问（在线检查，不要靠记忆判断）
- 锚文本是否与目标页面**当前**的 H1 一致（ID 与目标页面的对应关系容易漂移——H1 改名，或内容迁移到新 ID，都很常见；见"常见错误"）
- 是否引用了二手页面 / 销售页面 / 跨厂商推断
- 逐字引用块是否与官方当前版本**逐字符**一致（包括大小写、省略号、标点）

### §2 问答 / 章节匹配

- 答案是否切题 / 是否过度作答 / 是否跑题 / 反向交叉引用（"见 §Y 中的 §X"）是否闭环、没有死链

### §3 事实正确性

常见声明类型 → 核实锚点：

| 类型 | 锚点 |
|---|---|
| 数字 / 阈值 / 额度 / 延迟 / 窗口期 | 官方规范页面（注意地区/版本/生效日期分支） |
| 字段名 / API 名 / 枚举值 / 整数常量 | API 参考 / schema / IDL 当前版本 |
| 流程 / 适用范围 / 例外情况 | 官方规范措辞 / 限制条件 / 排除条款 |
| 生效日期 / 切换时间点 | 变更日志 / 博客 / 公告 |
| 命名 / 术语 / 是否与改名后的术语对齐 | 官方当前命名规范 |
| 责任归属 / 计费链路 | 从多个角度交叉论证：规范页面 + schema + 实际用户可见行为 |

### §4 整体一致性

- 术语全篇一致 / 中英混用是否合理 / 引用块各自可独立阅读 / 内部交叉引用闭环

## 工作流程（多轮 × 并行四维度 → 主agent仲裁修复）

触发本技能后，默认执行以下闭环，**最多连续跑 3 轮**：

```
第 N 轮 (N = 1..3):
  并行开 4 个只读 subagent，对全文重新扫描：
    §1 链接可靠性   §2 问答匹配   §3 事实正确性   §4 整体一致性
    ↓（每个 subagent 只返回结构化问题列表，不改文件）
  主agent：去重 + 跨维度仲裁 + 严重度定级
    ↓
  若本轮问题总数 = 0 → 提前收敛，结束循环
    ↓
  若存在 needs_human_decision=true 的项 → 批量列出，一次性询问用户，
  答复并入本轮修复方案
    ↓
  主agent 统一执行 Edit，修复本轮可自动修复 + 已获用户答复的项
    ↓
  输出本轮完整三段式报告（见下方「每轮输出」）
    ↓
  进入下一轮（跑满 3 轮后强制停止）
```

### 四个维度 subagent 的职责与执行细则

每个 subagent 各自专注一个维度，对全文重新扫描，只读、不修改文件。四个维度之间并行执行，但**单个维度内部**仍要遵守"先理解再审查""先提取声明再核实"的独立分工。

| Subagent | 职责 | 对应细则 |
|---|---|---|
| §1 链接可靠性 | 见上方「四维度检查清单 §1」 | 逐字引用块比对规则见「逐字引用截断的严重程度分级」，以及「常见错误」中的「把改写当成逐字引用」「逐字引用中的大小写细微差异」 |
| §2 问答/章节匹配 | 见「四维度检查清单 §2」，只判断切题与否，不判断事实细节 | 同时核对事实与匹配问题会让"答案切题但事实错了"这类问题溜过去，必须分开判断 |
| §3 事实正确性 | 先在自己的扫描范围内提取声明列表，再逐条在线核实（见下方细则） | 沿用原「声明提取 + 在线核实」规则，缩小到 §3 subagent 内部执行 |
| §4 整体一致性 | 见「四维度检查清单 §4」 | 跨章节冲突判定见「跨章节数字冲突：算 §3 还是 §4」 |

**§3 内部的声明提取与在线核实**：通读扫描范围一遍，把每个可核实声明提取到表格中（章节 / 类型 / 原文 / 引用来源），按类型分组；再对每条声明发起一次 WebFetch，搜索原文措辞而非摘要，记录逐字原文 + URL + 文档"最后更新"日期；不确定时标注"未找到官方依据"，不用训练记忆填空。

> **可核实声明的定义**：可量化或可对照外部权威来源核实的事实陈述——数字 / 阈值 / 字段名 / API 名 / 流程 / 适用范围 / 例外情况 / 生效日期 / 命名 / 责任归属。**不属于**可核实声明的：主观评价、设计意图、内部决策。这些不进入 §3 的核实环节，但仍受 §2/§4 覆盖。

> **§3 内部的并行子分派约定**：
> - 少于 5 条声明：在同一条消息内并行发起多个 WebFetch，不需要再拆子代理。
> - 5 条及以上声明：按 URL/类型分组，派发并行子代理分别执行 WebFetch + 逐字比对，每个子代理返回 `{claim, url, verbatim, official_last_updated, matches}`，不把官方页面全文带回 §3 subagent 的上下文。
> - WebFetch 结果不完整（截断/跳转登录页/命中过期缓存）时，用 WebSearch 找替代镜像（archive.org / 官方 PDF 版本 / 同一站点的另一路径），或标注"未找到完整依据"，不要基于不完整结果下逐字结论。

### 结构化返回字段

每个维度 subagent 返回的问题列表，字段统一为：

```json
{
  "dimension": "§1|§2|§3|§4",
  "section_id": "string",
  "current_text": "string",
  "issue": "string",
  "severity": "CRITICAL|HIGH|MEDIUM|LOW",
  "fix_suggestion": "string",
  "basis_url": "string|null",
  "needs_human_decision": false
}
```

### 主agent去重与仲裁规则

四个 subagent 的结果全部返回后，由主agent（不下放给 subagent）执行：

- 同一 `section_id` 被多个维度命中 → 这条拆分惯例不仅限于 URL，任何被多个维度命中的同一个定位点（不管是不是 URL）都适用；具体拆分格式参考「如何拆分单个 URL 的多维度问题」，按维度拆成 `[条目#]-a/-b/-c`，不合并。
- 同一事实在不同章节表述冲突 → 归 §4；单一事实与官方来源冲突 → 归 §3；两者都命中则两条都列（见「跨章节数字冲突：算 §3 还是 §4」）。
- `needs_human_decision=true` 的项（例如"未找到官方依据"且删/留没有明确判断依据、真正存在歧义需要人工取舍的情况）不在本轮自动修复，进入本轮批量暂停清单。
- 执行修复前，若发现多个问题的 `fix_suggestion` 指向有重叠的 `current_text`：
  - 若各自的改法互不冲突（只是文本范围相邻或部分重叠，但具体修改内容不矛盾），按顺序逐条执行修复，且每次执行前重新确认该段文本的当前状态——前一条修复可能已经改变了这段文本，不能用过期的旧文本做匹配。
  - 若各自的改法在语义上真正冲突（同一段落被建议改成不同的内容），不要自行选择哪个更对——把这种情况也标记为 `needs_human_decision=true`，纳入本轮批量暂停询问，把冲突的多个 `fix_suggestion` 都列出来，交给用户决定。

### 收敛规则

- 最多连续跑 3 轮。
- 任一轮结束、主agent完成去重仲裁后，若本轮 4 个维度汇总的问题总数（含 needs_human_decision 与可自动修复两类）为 0，立即结束循环，不再跑后续轮次。
- 跑满第 3 轮后无论是否还有问题，强制停止，剩余问题进入最终总结的"遗留项"。

### 批量暂停询问用户

主agent完成去重仲裁后，若本轮存在 `needs_human_decision=true` 的项：

- 一次性列出全部此类项（当前表述 / 问题描述 / 为什么无法自动判断 / 可选处理方式），一次性询问用户，不逐项打断，不分批。
- 用户答复后，答复内容并入本轮修复方案，与其他可自动修复项一起统一执行 Edit。

### 每轮输出

每轮结束都完整输出一次三段式报告 + 本轮修复情况，不裁剪：

> 根据被审计文档的结构选择标题前缀：问答类文档用 `Q1` / `Q2`；SDK/RFC/法规等结构化文档用文档本身的编号（例如 `§3.2` / `第 4.1 章` / `第 12 条`）。同一条目跨多个维度时，追加 `-a` / `-b` / `-c` 后缀（见"输出约定"中的"如何拆分单个 URL 的多维度问题"）。

```
### [章节编号/标识]：[标题]

【现状】[文档当前的表述，引用一句关键原文]

【问题】违反 §X（填写实际的维度编号 §1 / §2 / §3 / §4），严重程度：
- CRITICAL：核心数字 / 字段名 / API 名错误，直接误导计算或工程集成
- HIGH：死链 / 锚文本与当前 H1 不符 / 逐字引用与官方当前版本冲突
- MEDIUM：跨章节措辞不一致 / 引用了二手页面 / 推断与逐字引用混杂却未标注
- LOW：术语不一致 / 大小写细微差异 / 死的反向交叉引用

【建议修改 + 官方依据】
- 修改为：[改成什么]
- 依据：[官方 URL + 逐字原文 + 最后更新日期]
```

上面是单条问题的三段式格式；每轮实际输出时，把本轮全部条目按上面的格式逐条列出，再在其后追加本轮的整体汇总结构（含审计报告标题、严重度汇总、修复情况），如下：

```
### 第 N 轮审计报告
[各条目按上方三段式格式列出]

## 第 N 轮问题严重度汇总
### 必须修（CRITICAL / HIGH）
### 建议修（MEDIUM）
### 可选润色（LOW）

## 第 N 轮修复情况
- 已自动修复：[列表]
- 本轮经用户决策后修复：[列表]
- 遗留待下一轮：[列表]（仅当 N<3 且计划继续时）
```

> 上方「第 N 轮问题严重度汇总」与「第 N 轮修复情况」是对同一批问题按两个不同维度各切一次：前者按严重度（CRITICAL/HIGH/MEDIUM/LOW）分类，后者按处理状态（已自动修复/经用户决策后修复/遗留待下一轮）分类，两者内容有重叠但视角不同，不是重复展示。

### 最终总结

循环结束后（无论提前收敛还是跑满3轮），输出：

```
## 多轮审计总结
- 累计已修复：N 项
- 本次审计后仍遗留（3轮后仍未解决 / 官方依据缺失待补充）：N 项
  - 必须修（CRITICAL / HIGH）：N 项
  - 建议修（MEDIUM）：N 项
  - 可选润色（LOW）：N 项
- 收敛方式：提前于第 X 轮收敛 / 跑满 3 轮后停止
```

## 输出约定（分类规则）

实践中常出现的边界情况，提前说明：

### 如何拆分单个 URL 的多维度问题

当一个 URL 同时触发多个维度的问题时，**按维度拆分**，不要合并：

- `[条目#]-a` 链接有效性 / 锚文本与 H1 不符 → §1
- `[条目#]-b` 逐字引用块与原文不完全一致 → §1
- `[条目#]-c` 引用块对应的事实数字有误 → §3

拆分的好处：每一条能独立分级、独立修复；合并会让高严重度条目"吞掉"低严重度条目，导致后者得不到修复。

### 如何标注"未找到官方依据"

对于阶段 2 在线核实**未找到依据**的声明，不要用训练记忆填补，也不要静默删除。在三段式输出中作为独立条目列出：

- 【现状】文档原文
- 【问题】§3 / **MEDIUM**（默认；若是费率、API 名这类 CRITICAL 字段则升级为 HIGH）。注明"[日期] 在线搜索未找到官方依据"
- 【建议】删除该声明、找到内部权威来源为其提供逐字依据，或明确注明"未找到官方文档，视为基于观察到的行为"

同时在汇总中单独列一个"待补充依据"子分区（不计入三级分类），让作者知道这些是待处理项，而不是审计误判。

### 跨章节数字冲突：算 §3 还是 §4？

- 同一事实在不同章节出现**不同数字/不同术语** → §4（整体一致性/术语一致性）
- 单一事实**与官方来源冲突** → §3

示例：Q1 写费率 2.9%，Q4 写 2.5% → 这属于 §4（内部不一致），即使其中一个恰好与官方费率相符。如果两者都与官方来源冲突，则**同时**提出 §3（各自对照官方来源）和 §4（两者互相冲突）。

### 逐字引用截断的严重程度分级

不是所有截断都同等对待：

- **HIGH** —— 截断丢失了**适用范围限定语**（例如"in the US" / "for standard online transactions" / "starting July 1, 2021"）或**否定/转折词**（"unless" / "except" / "but"）——这类截断可能**颠倒适用边界**
- **MEDIUM** —— 截断丢失了上下文延续，但不影响核心结论
- **LOW** —— 截断的是纯粹的结尾延续句（"and applicable laws" —— 没有独立含义的结尾条款）

### 二手页面与一手来源配对交叉验证

三级帮助中心页面**不能单独**作为某条声明的依据，但可以与一手来源并列引用做交叉验证。可接受的形式：

```markdown
费率结构见一手定价页面（[Stripe Pricing](https://stripe.com/pricing)，逐字原文："Stripe charges 2.9% + 30¢..."），
面向用户的说明见[帮助中心概览](https://support.stripe.com/...)。
```

不可接受：只引用三级帮助中心页面而没有一手来源；或两者并列引用却不说明哪个才是权威依据。

## 常见错误（实践中踩过的坑）

### 内容迁移到新 ID，旧 ID 仍然存在

平台经常**保留旧的答案 ID 不变**，而把新内容/新概念放到**独立的新 ID** 上（不过有时也会反过来，保留 ID 而改动 H1）。实际案例：Google Play `answer/1153481` 的 ID 和 H1 都没变（仍是"Create an in-app product"），但新概念页面"Overview of one-time products"已经迁移到 `answer/16430488`——一份只引用旧 ID 并断言"H1 已统一为 one-time product"的文档，事实完全说反了。**修正**：对每个链接都要检查目标页面**当前**的 H1，并检查官方站点是否已经拆分出新页面——不要以为"旧 ID 还能打开=它仍是权威页面"。

### 把改写当成逐字引用

给一句改写内容加上逐字引用的引号。实际案例：文档写"Google 以支付货币结算"，但官方逐字原文是"Google issues wire transfer payouts in USD"——前者暗示"可配置"，后者意味着"强制以美元结算"。**修正**：逐字引用号内的文字必须与官方原文逐字符一致；改写应该以陈述句表达，不加引号。

### 逐字引用中的大小写细微差异

"...you can issue multiple..." 与官方的"You can issue multiple..."。开头的 `...` 标记了截断，但不代表可以改变大小写。**修正**：要么保留原文的首字母大写，要么用方括号 `[Y]ou` 明确标注大小写改动。

### 把推断当成逐字引用

官方文档有两个并列的标注小节（"Within 48 hours: ..." / "After 48 hours: ..."），合理推断出"自助渠道只在 48 小时内有效"，但官方文档**并没有这句原文**。如果文档没有标注"由 X / Y 组合推断而来"，读者会把这条推断当作逐字原文传播。**修正**：明确标注推断段落为"由 X / Y 组合推断而来"，并与逐字段落在视觉上分开。

### 把帮助中心页面当作一手规范

帮助中心/FAQ 页面是面向用户的二手页面（三级），不能单独作为技术细节的依据。实际案例：引用帮助中心的用户导向页面来推导 API schema 字段语义，经常导致不准确。**修正**：技术细节必须基于开发者文档/API 参考（一级）；帮助中心页面只能作交叉验证辅助。

### 用训练记忆填数值

"一般来说" / "据我所知" / "应该是 2.9%" 这类措辞 = 用训练记忆填空。训练数据有截止日期；费率/阈值/字段名经常变化。**修正**：每个可核实的数字都必须在阶段 2 在线核实；找不到依据时标注"未找到官方依据"，而不是猜测。

### 边读边核实

为了省时间把阶段 2/3/4 合并——同一份注意力边理解边审查，更容易让幻觉自我确认。实测：错误率比独立轮次更高。**修正**：把四个阶段物理分开，每个阶段只关注一个维度。

## 速查表

| 任务 | 工具 |
|---|---|
| 提取声明 | 通读全文一遍，按类型归入表格 |
| 核实链接可访问性 + 比对逐字原文 | WebFetch |
| 检查近期变更 / 找到当前正确页面 | WebSearch + 记录核查日期 |
| 并行核实多条声明（< 5） | 在同一条消息内并行发起多个 WebFetch |
| 并行核实多条声明（≥ 5） | 派发并行子代理，返回结构化摘要 |
| 跨章节声明冲突 | 在阶段 1 的表格基础上，检查同类型声明是否互相矛盾 |
