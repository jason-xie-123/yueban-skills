# docs 文件格式盘点与 AI 友好化改造

> ⚠️ **仅显性触发**：只有用户明确输入 `/yueban-docs-format-conversion`，或明确点名要用这个 skill/要做一次文件格式盘点转换时才执行下面的流程。不要仅凭"这个目录 AI 读不懂""把这些文档转成 md"这类泛化的自然语言请求就联想触发并直接开始批量转换——先向用户确认是否要跑这套流程，不要自作主张，这套流程涉及批量转换和删除原文件，代价比读一下文件内容大得多。

## 使用场景

用户想让某个文档目录（默认是 `docs/`，也可能是用户指定的其它目录）里混杂的 HTML、Word（docx）、Excel（xlsx）、PDF 等格式，转换成更利于 AI 直接读取理解的格式（优先 Markdown）。这不是"转一个文件"的一次性小任务，而是一轮**盘点 + 分类判断 + 批量转换 + 逐项核对 + 更新说明文档**的完整流程。

## 核心判断规则（先分类，再决定转什么）

对目录下每个非 md 文件，按以下顺序判断：

1. **带真实用户交互的 HTML**（点击展开/收合、表单、依赖用户操作才能看到内容的 demo 页面）→ **保持 html，不转换**。
   判断标准是"用户是否需要动手交互才能看到全部内容"，不是"有没有 `<script>` 标签"——JS 只在 load/resize 时自动跑一次（比如画连接箭头）不算交互。

2. **纯静态版面型 HTML**（div/css 画的方框图、泳道图、多分区架构图，价值在于"谁在哪一层、箭头指向谁"这种空间排布，没有用户交互）→ **转 PDF**，不要转 md。
   转 md 会把版面拍扁成嵌套列表，丢失空间信息，所以这类必须保留视觉版面。渲染尺寸要按原页面设计宽度来（不要臆造一个"内容实际宽度"），先用无头浏览器打开原页面在默认/设计视口宽度下测量 `document.documentElement.scrollWidth/scrollHeight`，再用测得的宽高截整页 PDF——很多多分区版面依赖固定视口宽度触发响应式布局，随意改宽度可能导致布局跟原样不一致。转完截图核对版面和文字是否完整。

3. **用 Mermaid.js 等图表库渲染纯文本图定义的 HTML**（页面里能找到 `mermaid.initialize` 之类调用，图的定义本身是文本化的 `sequenceDiagram`/`flowchart` 等）→ **转 md**，保留 ` ```mermaid ` 代码块，不要转 PDF。
   文本源本身就是无损的结构化描述，转 PDF 反而是把可编辑文本栅格化成图片，是倒退。先看清楚一个"方框图"是不是其实是 Mermaid 渲染的，不要单凭"看起来像架构图"就归到第 2 类。

4. **文字/表格为主的静态 HTML、docx** → **转 md**（pandoc `html→gfm` / `docx→gfm`）。
   先检查表格是否含合并单元格/嵌套表格/多级表头——pandoc 对这些的支持很差，常会静默拍平或丢内容、不报错。含这类表格的文件，转换后要重点核对表格部分是否失真；如果表格的版面结构本身就是信息（比如靠合并单元格表达分组关系），转 md 会丢失这层信息，应该按规则第 2 条当版面型内容转 PDF，而不是硬转 md。
   **同名不同扩展名的输出冲突**：转换前检查目标目录里是否已存在同基础文件名的其它文件（比如 `report.html` 和 `report.docx` 并存），两者都转 md 会都落地成 `report.md`、后转的静默覆盖先转的。盘点阶段发现这类同名对时，先跟用户确认两者是不是同一份内容的不同格式（是→只转其中信息更完整的一份，另一份直接保留原格式或删除；不是→给其中一个输出加区分后缀，如 `report-html.md`/`report-docx.md`），不要在没确认的情况下先转再看谁把谁覆盖了。

5. **xlsx** → 先看结构是否单一（单 sheet 或多个同构 sheet、纯表头+数据行，没有合并单元格/公式引用/透视表/靠样式承载信息），再看行数决定落地格式：
   - 结构单一、行数不大（几百行量级）→ **转 md 表格**。
   - 结构单一、但行数偏大（几千行以上，纯表格只是行多）→ **转 CSV**，不要硬转 md 表格：大表格里 md 的 `|` 分隔符和对齐没有额外语义价值，反而比 CSV 更占 token；多 sheet 时每个 sheet 各转一份 CSV（文件名带上 sheet 名后缀），保留 sheet 边界，不要拼成一个巨大的 md 文档。
   - 结构复杂（多 sheet 互相有公式引用、透视表、合并单元格、样式承载信息等）→ 保留原始 xlsx，不强转。

6. **pdf** → 先判断是"原始凭证/报表类"（银行流水、对账单、财务报表扫描件，页数可能几十到几百页，密集表格）还是"设计文档/说明类"（几页到十几页，文字+表格为主，非扫描件）：
   - 原始凭证/报表类，尤其页数大、转换收益低、且会产生体量巨大的重复文件 → **保留原始 PDF，不转换**，需要内容时用 `pdftotext` 按需抽取，不生成常驻副本。
   - 设计文档/说明类 → **转 md**（pandoc 不支持 pdf 输入，用 `pdftotext -layout` 抽取后手工整理成 md 标题/表格结构）。转之前先肉眼确认原 PDF 是单栏排版——`-layout` 对双栏/多栏版式会把两栏内容交错拼接成错乱顺序，且不报错；遇到多栏 PDF，抽取后要先按视觉版面重新排列好顺序，再动手整理成 md，不要直接基于交错文本臆测结构。

7. **纯图片格式**（png/jpg 等，drawio 导出图之类）→ 默认非文本格式不转换，但要打开看一眼图里画的是什么内容，按第 4 步「docx 内嵌图片二次处理」同一套判断标准分类：
   - 单纯的流程图/决策树/状态机（框+箭头，比如 drawio 导出的流程图）→ 转成 Mermaid，原图可删除。
   - 表格截图 → 转成 md 表格，原图可删除。
   - 纯文字/公式笔记截图 → 转成 md 正文文字，原图可删除。
   - 真正的 UI 原型/线框图、发票样例、多分区系统架构板（价值在整体版面而非流程）→ **保留原图，不转换**。
   - 拿不准图里到底是流程图还是版面型架构图时，判断标准同规则第 2/3 条：图的信息本质是"节点+连线关系"（可以无损转成文本化的 Mermaid）还是"空间排布本身就是信息"（转文本会丢失版面），前者转 Mermaid，后者保留原图。

不确定某个文件该归哪一类时（尤其是"看起来是方框图但也可能是 Mermaid"这种），**先打开文件看源码确认**，不要凭文件名或截图印象拍板。

## 执行流程

1. **盘点**：遍历目标目录，列出每个非 md 文件的路径、当前格式、关键特征（是否交互、页数/行数、是否扫描件等），按子目录分组整理成表格（可以直接用 AskUserQuestion 或对话形式跟用户过一遍判断结果，尤其是模棱两可的文件，不要自己完全拍板）。盘点时顺带标出基础文件名（不含扩展名）相同的文件组（如 `report.html` + `report.docx`）——这类会在第 3 步转换时争抢同一个输出文件名，见规则第 4 条的处理方式。

2. **检查工具是否就绪**：转换会用到 `pandoc`、`pdftotext`（poppler-utils）、`openpyxl`（或等价 python 库）、`@mermaid-js/mermaid-cli`、headless Chrome，正式转换前先确认这些工具本机可用，缺什么装什么（或提示用户装），不要执行到一半才发现某个工具没装。

3. **按分类执行转换**：
   - docx/文字类 html → md：`pandoc <in> -o <out>.md`（或 `-t gfm`），检查生成的 `*_assets/media/` 图片是否正确提取。
   - 方框图/泳道图类 html → pdf：headless Chrome 按原页面设计宽度渲染，先测量 `scrollWidth/scrollHeight` 再据此截整页 PDF（具体做法见规则第 2 条）。
   - xlsx → md/csv：用 openpyxl（或等价工具）读取后拼成 md 表格或 csv（按规则第 5 条的行数判断），勾选框/布尔列转成 `Y`/空这类清晰记号。
   - pdf → md：`pdftotext -layout` 抽取后手工整理结构。
   - Mermaid 语法务必用 `@mermaid-js/mermaid-cli` 逐个渲染验证，不要只凭肉眼看代码块（`mmdc` 依赖 Chromium/puppeteer，无网络或沙箱环境里可能因缺依赖直接失败，用前先确认能跑通）。注意**渲染成功只代表语法合法，不代表语义跟原图/原文本一致**——渲染通过之后仍要走下面第 4 步的人工内容核对，不能把"渲染没报错"当成核对完成。
   - **中文文件名/路径处理**：本仓库文件名大量是中文+空格+括号（如 `Bilings详细设计（副本）.docx`），命令行调用时路径必须加引号；`pdftotext` 等工具的默认输出编码不一定是 UTF-8，中文可能被静默转成乱码却不报错，转完一定要打开结果肉眼确认中文正常显示，必要时显式指定 `-enc UTF-8` 之类的编码参数。

4. **逐项核对无损**，核对方式按格式而定：
   - docx→md：用 pandoc 把原 docx 转纯文本，与新 md 逐段 diff，确认正文内容一致。**"允许表格/排版语法差异"这个豁免只适用于语法层面（比如 `|` 分隔符、缩进），不能用来放过表格内容本身的差异**——表格部分要单独核对：把原表格和新 md 表格都转成一份纯数值/文字的单元格集合（比如都转一遍 csv）做逐格比对，确认没有单元格被拍平、合并或丢失，再回头看正文段落的 diff。
   - pdf→md：全文做 token 级比对，比对的参考文本不要只用同一个 `pdftotext` 再抽一次（这样测不出 `pdftotext` 本身漏抽取的内容，比如图注、页眉里的表格），应该额外肉眼通读一遍原 PDF 确认页眉/图注/脚注都被覆盖到；剩余差异应该只是原 PDF 强制换行导致的断词。
   - html/pdf→pdf（版面类）：截图核对版面和文字完整性。
   - xlsx→md/csv：逐行核对行数和关键字段无遗漏；多 sheet 拆成多个 csv 的，确认每个 sheet 都有对应文件、没有漏转。
   - 图片→Mermaid/md 表格/md 文字：逐张跟原图比对内容和逻辑关系（箭头方向、分支条件、表格数值）是否一致，不要只看"转出来了"或"mermaid-cli 渲染没报错"就当核对通过——渲染成功只说明语法合法，不代表语义跟原图一致。

5. **docx→md 转换后的内嵌图片二次处理**：docx 转 md 时会把内嵌图片原样提取成 `*_assets/media/image*.png`。逐张检查后按以下原则决定是否进一步 AI 友好化：
   - 单纯的流程图/决策树/状态机（框+箭头）→ 转成 Mermaid（`flowchart`/`stateDiagram-v2`），原图删除。
   - 表格截图 → 转成 md 表格，原图删除。
   - 纯文字/公式笔记截图 → 转成 md 正文文字，原图删除。
   - 真正的 UI 原型/线框图、发票样例、多分区系统架构板（价值在整体版面而非流程，同判断规则第 2 类）→ **保留原图**，不要强转。
   - 如果原 docx 里一张逻辑上完整的流程图被拆成了多张图片（分页截断），转 Mermaid 时要根据上下文业务规则核对衔接处，拼接还原成一张完整图，并在正文加说明，不要留下断裂的两张图。

6. **检查交叉引用**：删除原文件前，用 `grep -r`（包含二进制文件用 `-a`，不要只 grep `*.md`）在**全仓库**范围搜一遍有没有其它文件引用过这个原文件路径或文件名——不止是 md 里的相对路径链接（`[详细设计](Bilings详细设计（副本）.docx)`），还要覆盖：其它非 md 文件（另一份 docx/xlsx 内部的超链接、CI 配置、wiki）、图片被 `![]()` 引用的情况、以及仓库里的 git submodule（submodule 内部可能单独引用了父仓库 docs 下的文件，需要单独进 submodule 目录搜一遍，父仓库的 grep 覆盖不到）——和 `yueban-docs-freshness-audit`/`yueban-proj-prune-historical` 一致，submodule 清单不要手写，每次从 `.gitmodules` 动态取得并排除 `deprecated/` 前缀（历史/冻结模块不需要做交叉引用检查）：`git config -f .gitmodules --get-regexp '\.path$' | awk '{print $2}' | grep -v '^deprecated/'`。有引用的话，把链接同步改成转换后的新文件路径，不要留下指向已删除文件的死链接。

7. **删除原文件前先确认，且确保能真正回退**：
   - 删除前先跑 `git status`/`git diff` 确认要删的原文件在仓库里**没有未提交的改动**——"删了还能从 git 历史找回"这个前提，建立在原文件当前内容已经被 commit 过；如果原文件本身有未提交的修改（比如用户正在编辑），核对无损核对的是旧内容，删除后未提交的改动会真的丢失且找不回来。发现有未提交改动时，先跟用户确认这些改动要不要保留/合并进转换结果，不要直接删。
   - 转换核对无误、交叉引用也处理完、确认无未提交改动后再删除原始文件。**每轮转换涉及批量删除原文件属于有一定不可逆性的操作**，不要一次性对几十上百个文件做一次笼统确认——按子目录或小批次（建议每批 ≤10-15 个文件）分批列出"哪些文件要删、转成了什么"跟用户确认，确认一批删一批，缩小误删的影响范围。原始凭证类 PDF、保留原图的情况不涉及删除。
   - 转换过程中产生的中间产物（headless Chrome 截图、mermaid-cli 渲染缓存、`pdftotext` 临时文本文件等）用完即清理，不要让它们残留进最终 commit；如果中间产物是从原始凭证类文件（银行流水、对账单等）里抽取的明文缓存，处理完更要主动删除，避免残留敏感信息。

8. **更新目录说明文档**（如 `docs/README.md`）：全部处理完后，回来更新对应的文件列表说明，把新格式、保留 html/pdf/图片原因写清楚，方便后来者（包括未来的 AI）不用重新盘点就知道每个文件是什么状态。如果目标目录本身没有现成的说明文档，先问用户要不要新建一份，不要默认一定有并直接去改。
